User: Within this, let's first look at hosting the mobile push notifications part — I want students to get notified about new events.

Assistant: Push notifications on the web are possible through the Push API and service workers. You'd need:

1. A service worker registered in the React app
2. A VAPID key pair generated on the server
3. A subscription endpoint stored per browser
4. A library like `web-push` on the Express side to send messages

There are some caveats: iOS Safari only supports web push for installed PWAs, and since you decided students don't have accounts, you'd be storing anonymous subscriptions. It's doable but it's a meaningful chunk of work.

User: Notifications should be sent within 5 minutes of an event being posted.

Assistant: That's achievable — you'd trigger the push send right after the event is saved, so latency would be seconds rather than minutes. The main cost is the setup work, not the delivery speed.

User: Actually, let's switch from MongoDB to PostgreSQL. Our data really is relational and the college server already has Postgres installed.

Assistant: That's a good reason to switch — having it pre-installed removes a setup step, and foreign keys between events and organisers will keep the data consistent. With Express, you can use `pg` directly or a query builder like Knex. Here's a first pass at the schema:

```sql
CREATE TABLE organisers (
  id SERIAL PRIMARY KEY,
  name TEXT NOT NULL,
  email TEXT UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,
  club_name TEXT NOT NULL
);

CREATE TABLE events (
  id SERIAL PRIMARY KEY,
  title TEXT NOT NULL,
  description TEXT,
  category TEXT NOT NULL CHECK (category IN ('tech','cultural','sports','academic')),
  starts_at TIMESTAMPTZ NOT NULL,
  ends_at TIMESTAMPTZ,
  venue TEXT NOT NULL,
  image_path TEXT,
  organiser_id INTEGER REFERENCES organisers(id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ DEFAULT now()
);
```

User: Next, let's work on the API design.

Assistant: Here's a REST API that covers the MVP:

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | /api/events | none | List upcoming events, supports `?category=` |
| GET | /api/events/:id | none | Event details |
| POST | /api/events | organiser | Create event |
| PUT | /api/events/:id | organiser (owner) | Edit event |
| DELETE | /api/events/:id | organiser (owner) | Delete event |
| POST | /api/auth/login | none | Organiser login |

For auth, I'd use sessions with an httpOnly cookie rather than JWTs, since the frontend and API are served from the same origin.

User: Let's go with session cookies for auth.

Assistant: Session cookies it is. You can use `express-session` with `connect-pg-simple` to store sessions in Postgres, which keeps everything in one database on the server.

User: Every API response must be JSON, even errors.

Assistant: Good rule. I'd add a final error-handling middleware in Express that catches everything and returns `{ "error": { "message": ..., "code": ... } }` with the right status code, so the frontend never has to parse HTML error pages.
